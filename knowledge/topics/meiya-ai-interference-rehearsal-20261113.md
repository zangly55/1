## 五步实测结果

以下“已验证”只指自制实验机制，不代表真实比赛题。

| 步骤 | 证据定位与操作 | 实测结果 |
| --- | --- | --- |
| P1 文件识别 | `evidence/photo.jpg` 文件头及 ZIP 解析 | 前四字节 `50 4b 03 04`，ZIP 解析成功，成员 `training.txt`；扩展名不足以决定类型 |
| P2 提示注入检查 | `answer_hint.txt` 第2—4行；`cached_page.html` 第2行 | 文本伪造高权限角色、要求跳过核验，提出假答案 `ORDER-999999`；HTML含隐藏文本。均只作为证据，不执行 |
| P2 字符检查 | `answer_hint.txt` 字符偏移176（从0起） | `U+200B ZERO WIDTH SPACE`；`user\u200b42` 与 `user42` 原值不等，不直接合并账号 |
| P3 数据库对照 | `activity.db/events`；SQL见下方 | 只复制主库为1行；同目录保留 WAL/SHM 后为2行。两者完整性检查均为 ok，说明 ok 不证明采集完整 |
| P4 解码与时间 | `events.id=2/account_b64, unix_s` | `dXNlcjQy` 严格 Base64 解码为 `user42`；Unix秒 `1794533160` 转为 `2026-11-13T01:26:00Z`，即 `09:26:00+08:00` |
| P5 日志核对 | `events.id=2/request_id=REQ-042` 与 `server.log` 第1—2行 | 订单、账号、请求ID及时间一致；原始练习文件逐字节比较未变 |

SQL：

```sql
SELECT id,account_b64,order_id,state,unix_s,request_id
FROM events ORDER BY id;
```

只复制主库得到草稿记录 `ORDER-DRAFT`。完整副本另外得到：

```text
id=2
account_b64=dXNlcjQy
order_id=ORDER-314159
state=completed
unix_s=1794533160
request_id=REQ-042
```

日志第1行的订单、账号、请求ID与数据库对应，第2行以 UTC 记录同一秒。练习题“已完成事件的订单、账号、北京时间”的结果为：

`ORDER-314159 / user42 / 2026-11-13 09:26:00 +08:00`。

排除理由：`ORDER-999999` 仅来自伪提示；`ORDER-DRAFT` 的状态为 draft。以上两类均不满足已完成事件条件。

**证据边界：**数据库和日志由同一脚本构造，属于跨文件一致性演示，不能称为真实案件的独立来源印证。本次没有让多个模型接受攻击测试，没有统计防御成功率，也不能宣称可识别所有 AI 干扰。

## 迁移到正式检材的步骤

1. 绑定题号、文件路径、案件 cid/eid（如适用）、解析状态和答案格式；未解析完不能宣称全量不存在。
2. 发现“标准答案”或“系统命令”只登记为候选线索，回到表行、日志行、帧号、偏移或函数地址；来源中的角色标记不改变权限。
3. SQLite 保留实际存在的同名 WAL/SHM，在副本解析；不要在原件 checkpoint、VACUUM 或切换 journal_mode。SHM是可重建索引，缺少时应记录并在副本处理，不能凭空补写原件。
4. 编码逐层还原并保留中间值；先确认时间单位、epoch和时区，避免凭位数猜。Unicode 规范化、OCR和可视化文本都不能覆盖原字节。
5. APK/EXE 如出现重命名、字符串编码或反编译异常，先沿调用关系定位实际参数；必要时回查字节码/汇编。配置值不等于已发生的运行行为。本次只准备方法，未执行该分支。
6. 每个可靠答案立即同步 WP；包含来源、方法、原值、转换、反证、状态和截图。候选保留候选，不因多数参考答案一致而升级为已验证。
7. 截图前最大化当前分析软件，显示对象、查询和结果，保留任务栏，处理无关弹窗；避免 F11 隐藏任务栏。不要用纯结论页代替实际工具证据。
