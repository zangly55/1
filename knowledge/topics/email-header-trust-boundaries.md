# 邮件头取证：Received 与 Authentication-Results 的信任边界

- 建立：2026-11-22；整理者：Codex。
- 状态：两份 RFC 一手文档核对；未解析真实邮件、复验服务器日志或执行密码学验证。
- 触发问题：邮件经过哪些中继、哪个 IP 可作为连接线索、认证结果能否证明发件人。
- 适用范围：依下列 RFC 解释 SMTP 邮件头；实际 MTA 实现、配置与采集完整性必须另查。本卡固定引用版本，不声称覆盖所有后续扩展。

## 文档要点

1. SMTP 接收方将 Received 加在顶部；合规追加时上新下旧。FROM 可同时包含 EHLO 声称名称和从 TCP 连接取得的地址，两者性质不同。保留日期偏移；Return-Path 承载 MAIL 的反向路径，不能把信封地址与消息头地址自动等同。传输层认证不自行证明完整中继链或实际操作者。[RFC 5321 §4.4、§7.1—7.2](https://www.rfc-editor.org/rfc/rfc5321.html#section-4.4)
2. Authentication-Results 传达某服务已作的检查结果；authserv-id 是标识，不是身份认证凭证。使用结果需确认可信产生者、传递链与边界过滤；同名字段也可能伪造。附件内旧结果与本次投递分开；pass 也不能保证邮件内容可信。[RFC 8601 §1.2、§2.5、§4.1、§5、§7.1—7.2](https://www.rfc-editor.org/rfc/rfc8601.html#section-7)

## 可复用核查流程（本卡综合建议）

1. 登记案件、邮件原始位置、导出方式与是否含完整头。保留原字节和字段次序；分析副本记录每个同名字段的行号/偏移，避免字典覆盖重复字段。
2. 从接收侧可证实的系统开始，利用本案 MTA 日志与配置确认其插入的字段，再向外逐跳标注可信程度。单凭头部位置或熟悉域名不能建立可信链；无法确认边界时，最底部地址只能列候选。
3. 表格分列“原始字段”“声称主机”“接收方记录的连接地址”“原始时间/偏移”“日志关联”“状态”。归一化时间用于比较，原次序与原时区同时保留；异常时序先列缺口。
4. 对认证字段记录 authserv-id、方法、结果及被检查的标识。先证实字段来源，再判断该方法覆盖什么；没有实际复验时写“所采邮件头报告 pass”，不要写成本次签名验证成功。
5. 将连接来源、域认证、邮箱使用者、自然人身份分别表述。若问题需定位操作者，仍须本案账号、主机或访问记录补证。

## 反例与验证限制

攻击者可自行编写看似内部域名的认证结果；转发附件可携带旧结果。两者均需来源核查，不能按关键词直接升级为已验证。上面的逐跳核查是从规范导出的工作建议，并非已实施实验。

本轮未连接邮箱、查询实时 DNS、发送邮件、运行附件或获取私密原件；没有合成实验或真实检材测试。未证明任何具体邮件的来源、签名、投递时间或操作者。公开页仅含通用方法与来源，后续若归档实例须另行脱敏。
