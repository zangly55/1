# 应用分析报告草拟

## 输入前提

输入必须已经完成证据审查，至少包含：用户问题、应用身份与版本、专家证据记录、结论强度、冲突、边界、未回答问题，以及产品 Skill 返回的执行状态。缺少关键来源或结论尚未定级时停止草拟，并返回待补充项。

草拟前读取 [报告模板](references/报告模板.md)。输入中的证据等级、结论强度和审查结果视为调用方已经确定的约束，不在本 Skill 中重新裁决。

## 边界

- 不调用静态、源码、脱壳、动态、抓包或 Frida Skill。
- 不创建、查询、停止产品任务，不发起或校验授权。
- 不读取未治理的原始 CLI 输出，不补造缺失的来源引用、任务 ID 或产物。
- 不修改专家给出的 evidence level、结论强度和冲突裁决，不自行生成 E4。
- 输入证据不足时使用“未提供”“待验证”或“仅当前会话可复核”，不将计划写成已执行。
- 生成 HTML 时必须保证窄视口可读：应用信息表首列保持至少 110px，允许项目名称换行；路径、哈希和命令可断行，不得出现逐字挤压、横向溢出或内容重叠。

## 草拟规则

1. 按模板组织应用与研判问题、结论摘要、静态概况、源码机制、运行行为、网络数据流、Frida 验证、重点发现、证据缺口、证据索引和材料限制。
2. 事实、解释、风险和建议分开；面向用户的正文使用“结论强度”和自然语言依据，不直接展示 E1/E2/E3/E4、cid、aid、tid、evidence_id、raw_cli_response_ref 等内部证据和运行标识。内部标识仅保留在受控审计元数据或用户明确要求的附录中。
3. 静态能力、源码机制和本次运行观察分开，不把“未观察到”写成“不存在”。
4. 通信、敏感字段、数据来源关联和政策不匹配分别表述，不把请求存在直接写成数据外传。
5. 如实披露失败、阻塞、截断、混淆、加固、TLS、交互覆盖和仍在运行的任务状态。
6. 简单问题不强制生成完整报告；调用方明确要求综合报告时输出正式报告，不使用“草稿”措辞。

## 输出

用户未指定报告格式时，输出一个 UTF-8 编码的自包含 HTML 文件，样式全部内联，不引用外部 CSS、脚本、字体或图片，可直接在浏览器打开和打印。只有用户明确指定其他格式时才改变交付格式。报告只能复述和组织输入中已经审查的事实与结论，不能替代专家的证据审查或最终定级。

报告生成过程中也不得向用户输出内部证据分级、任务 ID 或“交叉印证结论”等编排术语；统一改写为“静态线索”“源码分析”“运行时观察”“多来源相互印证”等用户可理解的表达。
