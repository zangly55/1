# x64dbg 动态调试

通过 MCP 控制 x64dbg，验证静态分析提出的假设，记录运行证据并回填联动交接清单。工具名以当前运行时可见名称为准，本文使用裸名；首次调用前读取工具描述，核对参数、状态要求和返回语义。

## 工具选择与发现

核心流程只列常用方法。需要选择其他能力，特别是条件/内存断点、断点清理、内存与指针、线程切换、导入导出、补丁恢复、书签或数据库保存时，先查 [x64dbg 工具索引](../../references/x64dbg工具索引.md) 的对应分类。

索引保留已记录的方法名与用途，不代表当前服务端已提供全部方法。通过运行时工具发现/描述入口确认所选方法；若工具列表不完整且可调用 `ListCommandsByCategory`，用它查询相关类别，再读取目标工具描述。索引未列出的方法仍可使用；只有发现结果或调用错误确认工具不可用时，才将其记为能力缺口。

## 状态与事件

每次操作前确认已有状态证据足以支持该操作。优先读取最近一次工具响应中的 `[state]` 和 `[event:*]`，确认目标、暂停位置及事件原因；状态仍可信时直接继续，不在每个动作前重复查询。

以下情况调用 `GetDebugState`：首次接入；响应缺少状态或状态相互矛盾；调用失败、超时且结果不能确定状态；用户操作了调试器或报告已经暂停；切换目标或间隔较久，之前的状态可能已失效。

| 状态 | 下一步 |
| --- | --- |
| `NO_TARGET` | 核对目标后用 `LoadBinary` 加载，或按任务用 `AttachProcess` 附加；已有正确目标时复用会话 |
| `PAUSED` | 可按需反汇编、读取内存、寄存器和调用栈，或单步验证 |
| `RUNNING` | 先用 `WaitForPause` 等待或用 `PauseDebug` 暂停，确认 `PAUSED` 后再读取内存、反汇编或检查寄存器 |

`run` 或等待调用返回不等于命中了目标断点：结合返回状态、事件原因和当前地址区分断点、异常、手动暂停与超时。仍为 `RUNNING` 时继续等待或暂停；状态不明时查询。新事件或用户操作使旧状态失效后重新确认。

需要等待事件时，按当前可用工具使用 `WaitForEvent`；是否有推送以实际运行时返回为准，无需猜测传输类型。设置符合任务的有限等待时间；超时后检查是否仍有可触发目标路径的动作，不无期限重复等待。

## 核心流程

### 加载与建立基线

1. 确认调试状态和目标；需要加载时调用 `LoadBinary`。
2. 从响应确认是否暂停；仍在运行时调用 `WaitForPause`，状态不明时调用 `GetDebugState`。
3. 确认暂停后，用 `ListModules` 核对模块与加载基址，按需用 `GetAllRegisters`、`Disassemble` 建立运行基线。
4. 与静态端对齐地址并同步符号，具体字段与换算见 references/联动交接清单模板.md。按运行时契约使用 `FindPattern` 核对字节签名，用 `CommentOrLabelAtAddress` 设置已核实地址的标签。

### 断点与 API 验证

1. 在已确认的暂停状态下，用 `SearchSymbols` 或 `EvalExpression` 解析符号，核对所属模块和实际地址。
2. 用 `SetBreakpoint` 设置目标断点，再调用 `run`。
3. 读取返回状态与事件，核对暂停地址是否对应目标断点。异常或其他位置的暂停不能当作目标命中。
4. 命中后按假设使用 `Disassemble`、`GetArguments`、`GetAllRegisters`、`GetCallStack` 或 `ReadMemory`；记录输入、输出及调用上下文。

### 单步与跟踪

- 确认 `PAUSED` 后，按是否需要进入调用选择 `StepInto`、`StepOver` 或 `StepOut`。
- 每步读取新地址、反汇编、状态与事件，再决定下一步；响应足够时无需额外调用 `GetDebugState`。
- 需要一段执行轨迹时，用 `TraceInto` 或 `TraceOver` 设置有限指令数，保留轨迹并核对结束状态。
- 使用 `DisassembleFunction` 前确认函数已分析；必要时先用 `AnalyzeCode`，或按运行时契约使用调试器的函数分析命令。

### 解包与内存修改

- 用 `AnalyzeModule`、`DetectOEP` 寻找入口和解包线索，将疑似 OEP 作为待验证地址；结合断点与实际执行确认后再用 `DumpModule` 保存派生样本。
- 修改内存前确认暂停并记录原始字节；用 `WriteMemToAddress` 修改后重新读取或反汇编核对，用 `GetPatches` 记录补丁。
- dump 和补丁产物写入工作区副本，不覆盖原样本；记录修改范围，区分原始运行证据和修改后的观察。

## 表达式与命令

- 用 `EvalExpression` 按实际符号、寄存器、标签或地址表达式求值后再访问；例如 API 符号、栈偏移或已设置的标签。数值基数和表达式语法以工具描述为准。
- `ExecuteDebuggerCommand` 接收 x64dbg 命令；MCP 工具应直接调用，不把工具名作为调试器命令传入。
- 异常影响验证时，先记录异常及其影响，再按需用 `SetExceptionBreakpoint` 配置特定异常，不用 `erun` 无差别跳过所有异常。

## GUI 与消息循环

目标等待用户输入、显示对话框或停留在界面时，运行超时可能只是尚未触发目标路径。先结合状态和事件判断，再选择：

- 用 `PauseDebug` 暂停检查，并记录这次暂停是否只落在消息循环；暂停本身不证明目标行为已执行。
- 根据静态定位与用户目标，在相关 API 或处理函数设置断点，再恢复并触发对应交互。
- 用户准备操作界面时，用 `WaitForEvent` 等待相关事件；非目标事件后仍需核对触发路径是否覆盖。
- 只需记录且运行时支持时，结合 `SetBreakpointCommand` 与 `SetBreakpointFastResume` 采集日志；需要寄存器或内存快照时使用真正暂停的断点。
- 已知关注数据地址时，可用 `SetHardwareBreakpoint` 验证实际访问；需要条件筛选或监视内存区域时，按工具索引选择相应断点。

动态证据不足时，可以返回 `re-ida-static-analysis` 补充调用链、符号或候选断点，再回到动态端验证。静态结果只支持代码层面的判断，不能替代本次运行事实。工具不可用、目标路径无法触发或缺少交互条件时，记录阻塞和下一步，交付带局限的结论。

## 交接与输出

每项发现写明实际地址、模块、指令行为，以及相关寄存器、参数、内存或调用栈如何支持判断；未读取的上下文保留为缺口。

按 references/联动交接清单模板.md 回填观察结果、裁决（证实/证伪/存疑）、真实依据和静态端需要修正的名称/注释。清单中的待验证项有可执行补证动作时继续循环；无法继续时说明原因和人工复核路径，不把未命中或超时写成行为不存在。
