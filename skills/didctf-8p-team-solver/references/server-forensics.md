# 服务器题：数据归属、事件、统计与恢复

仅在服务器/容器题、面板事件、交易统计或删除文件题中按需读取。这里是决策方法，不预置案件答案。

## 1. 先画数据归属，再搜索

记录外层宿主、嵌套虚拟机、分区、容器、应用及其数据目录的对应关系。通过容器配置、启动命令、MountPoints/bind/volume、可写层及镜像层确认归属；不要把某个 `overlay2/*/diff` 当全部运行时文件系统。宿主与容器中的同名面板可保存不同日志。

删除文件题先查应用实际存储实现：服务端数据库/上传目录、Docker卷、访问端浏览器存储或同步/备份。静态服务程序存在不证明用户文件保存在服务器；发现 localforage/IndexedDB/localStorage 后还要追踪调用用途，检查是否另有服务端或同步路径。结论限定到检材中的版本与部署。再决定查浏览器配置、应用备份、回收站还是文件系统恢复。

恢复检查点至少区分：任务完成 → 结果可枚举 → 目标对象被识别 → 内容可读且完整 → 时间元数据可归属。前一步不能替代后一步。签名恢复仅有内容时，不能用恢复/导出时间回答原删除时间；尚未看到目标文件时，不声称恢复成功或恢复为零。

## 2. 用事件链回答“删除后第一次”

先列所有可能的删除/清空事件：时间、对象、API、日志来源、会话及成功依据。区分删除日志目录、清登录日志、清操作日志、清错误日志；不能默认最新一次就是题干事件。

结合代码确认动作参数，再找符合题干对象的后继操作。保留原始行序和同秒记录；按时间排序时不得打乱同秒事件。范围内第一条残存记录不天然等于事件后的第一次操作。必要时合并轮转/压缩日志并去重，标明覆盖缺口。

## 3. 净利必须核对对象和计费粒度

先继承“接上题”的商户/账号范围，再统计活动记录。区分已售卡数、商品数、订单数、短信次数；不要按已售卡数直接乘按订单收取的费用。

将题干明确排除的费用与其余实际费用分别列出，追踪代码中的触发条件、默认开关、承担方和扣费位置。当前售价/成本只是当前配置，历史净利仍需订单、优惠、流水及当时配置。参考公式能算出同一个数不代表条件已被证明。

离线页解析需按实际表结构、聚簇索引、活动记录链与叶页覆盖核对，避免二级索引重复、删除残留混入；不把本案固定偏移解析器推广到其他版本。缺交易明细时交付可验证小计和条件公式，不把它写成已确认净利。

## 4. 备份与计划任务按来源分类

整套面板原生备份、站点目录手工tar、配置自动备份是不同候选。由创建请求、任务清单、完成日志和包内成员确定题干目标，再对导出包实算哈希，与清单值交叉验证；不能因文件名相似就只追一个候选。

计划任务查宿主cron、面板任务表/创建删除日志、容器调度器数据库及其脚本。当前任务不存在不等于从未配置；创建日志中的脚本可留有目标地址。`@boot`按启动触发解释，不能改称固定周期执行。

## 5. 情境验收

- 接上题指定商户，平台还有一个旧商户：只能统计指定商户；保留原题关系。
- 已售496张，代码按启用通知的订单扣一次费用，订单表空：不能确认496次扣费。
- 多天有不同清日志操作：先列事件对象，再选匹配事件及后继目录请求。
- 恢复100%，目标未见，应用当前构建将books写入浏览器存储：核对恢复归属/结果并转查访问端或备份，不以“再重启”作为循环策略。
- 两个备份包：查清单、成员和生成日志后选目标并计算哈希。
- 无时区安装值与UTC首启时间相邻：说明推断及冲突，不把相邻当绝对时区证明。
