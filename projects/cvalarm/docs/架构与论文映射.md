# 架构与论文映射

本文件把论文《持续视频监控中视觉语言模型异常告警的事件存在性、时间定位与部署评测综述》
的工程论述逐段落到代码上，并说明**哪些是照做、哪些是做了取舍、哪些没有实现**。
论文段落号以原文小节为准。

> 另有一份对齐 **导师汇报稿（工程方向）** 的逐条说明，见
> [工程方向对齐说明.md](工程方向对齐说明.md)：首版范围、证据回放、双时延、定位精度、
> 资源与模型记录、开发/测试隔离与独立测试报告。

## 1. 总体结构

```
                    ┌────────────────────── Stage1 ──────────────────────┐
逐帧检测 → 两级关联跟踪 → 多边形 ROI → 六状态在场计时 → 候选(粗窗口+轨迹先验)
                    │                                   ↘ 旁路抽样审计 ──┐
                    └───────────────────────────────────────────────────┘
                                                                        │
     候选 ──→ Stage2 非自回归区间打分 → Kadane 解码 → 存在性三向分流 ←──┘
                                     ├─ EVENT ──────────→ Stage3 证据核验 → 结构化卡片
                                     ├─ NO_EVENT ───────→ 静默抑制（留档）
                                     ├─ INSUFFICIENT ───→ Stage3 → 转人工卡片
                                     └─ SYSTEM_ERROR ───→ 重检队列（不判"正常"）
                                                                        │
     卡片/抑制/异常 ──→ 中控台 ──→ Stage4 人工反馈（Confirm/Dismiss/Uncertain）
                                     └→ 离线反思 → 候选规则 → 静态校验 → 回归门禁 → 原子发布
                                                                        │
                     全链路计量（帧/时长/GPU 秒/Token/人工分钟）→ 指标 + 成本 + 报告
```

## 3. 关键设计取舍

### 3.1 为什么 FSM 阈值按 ROI 配置，而不是全局一个

论文的 `T_threshold` 是"某条规程"的阈值。同一台设备上不同区域适用不同规程
（周界 45 秒、装卸区 1800 秒）。若用全局阈值，长滞留事件会在阈值远未达到时被触发，
后面只能靠规则再"往上卡"，结果是大量无效候选涌入 Stage2/3。
因此 `Roi.dwell_threshold_s` 逐区域设置，`Candidate.dwell_threshold_s` 随之携带。

### 3.2 为什么审计样本要"零化停留进度"

抽样审计的窗口里**没有状态机锚点**。如果照搬候选的打分方式（把 `t_enter` 设在窗口起点），
就会虚构出"已滞留满阈值"的证据，把负例分数整体抬高，标定出来的阈值随之失真。
所以审计样本在打分时停留进度项按 0 计，并在 `validity` 里标 `stale` 语义。

### 3.3 为什么遮挡率只在"应在场"的 bin 上统计

候选窗口是 30~60 秒历史，而阈值可能只有 10~45 秒。窗口前段本来就不该有目标，
把它计入遮挡率会让所有正常候选都被判成"看不清"。
把统计范围收敛到 `[t_enter, t_trigger]` 后，遮挡率才真正反映"目标在场但看不见"。

### 3.4 为什么身份关联要放在轨迹之上

长时遮挡必然导致跟踪器换 ID。若只在单轨迹内做 ReID，跨遮挡的累计时长会被清零，
"滞留 30 分钟"这类判断就永远做不出来。因此 `stage1._try_rebind` 在轨迹层之上做重绑，
并用"重现**之前**的外观记录"做判定，避免自证。

### 3.5 为什么 TTA 起点用 `t_trigger − 溢出量`

`t_enter + threshold` 在跨遮挡分段累计时会算早几十秒（把被扣除的间隔也算进去了），
于是真实时延会显示成负数。用"触发帧的累计值刚好越过阈值的物理时刻"才与部署口径一致。

### 3.6 为什么规则求值用优先级而不是"动作类型排序"

"可见性不足转人工"必须能压住低优先级的告警规则，否则夜间会给出确证结论
——这正是论文反复警告的"把看不清写成没发生"。所以结论由 `priority` 唯一决定，
动作类型只做平级次序（suppress > escalate > alarm），静态校验会提示"抑制规则优先级过低"
或"安全规则压不住确证规则"。

### 3.7 为什么不用 `r2` 的"候选数比例"

论文明确要求按时长加权。本实现用 `stage3_input_seconds / candidate_video_seconds`，
因为长窗口与短窗口对第三级的成本贡献差几个数量级，用个数比例会系统性低估。

## 5. 没有实现的部分与理由

1. **外部大模型本体**（VideoJev / Qwen2-VL / PARSEE-VAD / RoMod / GridVAD / CAPD）。
   这些需要权重与 GPU，且论文本身强调"其成绩对应特定测试条件"。工程提供的是
   **可替换接口 + 统一口径**：把模型分数灌进 `IntervalScorer`、把模型输出灌进
   `LLMVerifier`，其余分流、评测、成本、治理逻辑不变。
2. **模型内部机制研究**（常态偏见、表示-行为失调）。属于模型侧分析，
   工程侧能做的是把"画面事实"与"规程推断"强制分开、并把未决事项显式列出。
3. **参数微调与持续学习**。论文 §6.2 的遗忘问题在本实现中的工程答案是
   "冻结权重 + 更新外部非参数规则"，因此不提供微调路径。
4. **形式化验证**。规则校验是静态检查（死锁、优先级、覆盖度），不是模型检验。
5. **生产级控制台**。看板是只读演示件（标准库 http.server，无鉴权/无 TLS）。
